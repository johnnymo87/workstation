# az-reauth Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or
> subagent-driven-development) to implement this plan task-by-task. Tracked as a
> bead epic; `bd ready` is the source of truth for what is next.

**Goal:** Keep the Azure CLI login alive on the Mac and on the remote, with no
human action beyond the IdP sign-ins the gcloud refresher already asks for.

**Architecture:** A new launchd job on the Mac, `gcloud-reauth-az`, runs hourly.
When a login is due, it runs `az login` against a throwaway config directory,
and a new harness script, `az-login.mjs`, completes the browser half silently in
a background tab of the isolated Chrome that gcloud-reauth already keeps signed
in. The result is verified, stripped of access tokens, and merged into
`~/.azure/msal_token_cache.json` on the Mac and on the remote using az's own
lock protocol.

**Tech stack:** bash (writeShellApplication, no errexit), python3 (state,
probe and install helpers; stdlib only), node + puppeteer-core (browser half),
home-manager launchd agents, macOS Keychain for org-identifying values.

Design: `docs/plans/2026-11-19-az-reauth-design.md` (approved 2026-11-19). This
plan departs from it in one place: the az step is a **separate script and
launchd agent**, not a section of `refresh.sh` (see "Deviation from the
design"). Reviewed by adversarial-reviewer-opus on 2026-11-20 (three rounds; approved); its
findings are folded in below.

## Measured facts (2026-11-19/20) the plan depends on

1. **What kills az.** Conditional Access sign-in frequency, 86400 s. The error is
   `AADSTS70043 ... The token was issued on <T> and the maximum allowed lifetime
   for this request is 86400`.
2. **A silent login does not restart the clock.** A refresh token minted silently
   on 2026-11-19 17:45Z died by 2026-11-20 11:00Z, and Entra named its issue time
   as `2026-11-19T09:47:38Z`. That was the session's last real authentication:
   the isolated Chrome's History has `/common/login` FORM_SUBMIT visits at
   09:46:58Z and 09:47:22Z. So every token is **anchored** to the last real Entra
   sign-in and dies at anchor + 24 h. Reading the anchor from History errs early
   (by 16 s here), which is the safe direction.
   A second data point is pending: a token minted 2026-11-20 11:06Z is predicted
   to die at 23:08Z (the next `/common/login` visit, 23:08:24Z); a self-wake at
   23:20Z checks it. If the prediction fails, revisit Task 3 rule 5 before
   implementing it. The plan degrades safely either way: rules 5 and 6 still
   recover a dead token within about an hour.
3. **Silent logins leave no `/login` visit.** Both spike runs left only
   `/<tenant>/oauth2/v2.0/authorize` and `/<tenant>/reprocess` visits (verified by
   the reviewer against History). So rule 5 cannot trigger itself.
4. **The `ESTSAUTHPERSISTENT` cookie is not an anchor.** Its expiry moved to
   "now + 90 d" after a silent login (measured 11:06Z). Do not use it.
5. **Real Entra sign-ins happen about every 18-19 h** in the isolated Chrome, at
   the times the gcloud harness needed a human IdP sign-in (11-13 .. 11-19); the
   gcloud harness's own silent refreshes never touch Entra. So a token anchored
   to the latest sign-in normally has hours of life left when the next sign-in
   arrives.
6. **The silent browser half works.** az's authorize URL shows "Pick an account"
   with a tile `[data-test-id="<account>"]`; one click goes through `/reprocess`
   to az's loopback listener (`http://localhost:<port>/`) in about 1 s, and az
   exits 0. No password, no MFA. Two gotchas:
   - puppeteer's `ElementHandle.click()` and `page.click()` hang for the whole
     protocolTimeout in a background tab. e2e.mjs explains why and uses
     `Input.dispatchMouseEvent` press/release at the clickable point (`clickEl`).
     Reuse that approach.
   - The authorize URL **contains** `redirect_uri=http://localhost:<port>`, so a
     substring test for "localhost" passes while still on Entra. Compare the
     page's host, never the whole URL.
7. **The `BROWSER` stub works**, with a trap. Python's `webbrowser` (3.13) runs
   `shlex.split` on a `BROWSER` value containing `%s` and tries each browser in
   order until one returns success; a stub that exits non-zero or is not
   executable falls through to the human's **default browser** (`MacOSXOSAScript`).
   With stdin from `/dev/null`, az skips the subscription picker and exits 0.
   azure-cli 2.79 enables the WAM broker on Windows only.
8. **Cache format.** Both hosts keep a plaintext `~/.azure/msal_token_cache.json`
   (0600); the Mac does not encrypt it. One `RefreshToken` entry for the Azure
   CLI client `04b07795-8ddb-461a-bbee-02f9e1bf7b46`, keyed by
   home_account_id/environment/client (no secret in the key), identical across
   hosts for the same user.
9. **Checks are answered from cache.** msal returns a cached access token with
   at least 5 minutes left without touching the refresh token, and falls back to
   it when a refresh fails. So any check against a cache that holds an access
   token for the resource proves nothing about the refresh token. Task 2's probe
   runs against a copy with access tokens stripped.
10. **az's real lock protocol** (msal-extensions 1.3.1 `cache_lock.py`): an
    `O_EXCL` create of `<cache>.lockfile` (az waits up to 5 s, then proceeds
    anyway with a warning), then `flock`, then unlink. msal does **not** hold the
    lock across a network refresh: it reads the cache unlocked, then writes each
    token type in its own locked `modify`. So an az process that read the old
    cache before an install and refreshes after it can write an old-anchored
    refresh token back (last writer wins). The remote runs az routinely
    (lgtm-shepherd every 10 min, kubelogin). No lock prevents this; Task 4's
    `recovered` outcome detects it after the fact.
11. **az needs a profile.** `get-access-token` first looks up a subscription in
    `azureProfile.json` and fails with "run az login" when there is none for the
    user, whatever the token cache holds.
12. **Chrome History** uses a rollback journal (`History-journal`, no `-wal`).
13. **az versions.** 2.79.0 on both hosts (the `azureCliPatched` build in
    `users/dev/home.base.nix`, a `let` binding there, so the Mac job finds `az`
    through `${config.home.profileDirectory}/bin`). python3 is on the remote
    (`home.cloudbox.nix`).
14. **Nothing else uses `AZURE_CONFIG_DIR` today.** `workstation-ph89`
    (per-session az config) is unimplemented. If it lands, the install target
    must stay the shared `~/.azure`.

## Deviation from the design

The design put the az step inside `refresh.sh`. It is a separate script
(`assets/gcloud-reauth/az-refresh.sh`, package `gcloud-reauth-az`) with its own
launchd agent at minute 22, because:

- `refresh.sh` exits early on most runs (`not_due`, `fail_all`,
  `waiting_for_human`), so an az step there would need a hook on every exit
  path, and its failures would share the gcloud exit status.
- The keepalive sets the precedent: a separate script with its own copy of the
  alert helpers, sharing `$STATE` (alert pid files, `reauth.lock`).
- The design's trigger (b), "right after a human sign-in", becomes "the
  isolated Chrome's History shows a `/login` visit newer than the current
  token's anchor". That catches every real sign-in, including ones the gcloud
  refresher did not prompt for, within an hour; fact 5 leaves ~5 h of margin.

### Task 1: `az-login.mjs`, the browser half

**Files:** create `assets/gcloud-reauth/az-login.mjs`.

1. Args: `<url-file> <result-file>`, or `--raise` (see step 7). Env:
   `AZ_ACCOUNT` (required), `AZ_TENANT` (required), `REAUTH_CDP_URL` (default
   `http://127.0.0.1:9223`).
2. **Validate the URL before connecting to the browser** (pattern:
   `validateAuthUrl` in e2e.mjs, including its refusal of duplicated pinned
   parameters):
   - `https:`, host exactly `login.microsoftonline.com`;
   - path exactly `/<AZ_TENANT>/oauth2/v2.0/authorize`;
   - `client_id` = `04b07795-8ddb-461a-bbee-02f9e1bf7b46`;
   - `redirect_uri` parses as `http://localhost:<port>` with path `/` or empty;
   - `code_challenge_method` = `S256`, `response_type` = `code`;
   - scopes a subset of `https://management.core.windows.net//.default`,
     `offline_access`, `openid`, `profile`.
   On failure write `{outcome: "url_rejected", reason}` and exit 3.
3. Connect (`protocolTimeout: 30000`). Close only tabs that an earlier run of
   this script left for a human: host `login.microsoftonline.com`, path
   `/<AZ_TENANT>/oauth2/v2.0/authorize`, `client_id` the Azure CLI client. (The
   job's rule 6 keeps runs away for 6 h after a hand-off, so this does not race
   a human who is typing.) Also close the tab such a hand-off ends on after
   the human signs in: host `localhost` or `127.0.0.1` with `code` and
   `session_state` in the query. Leave every other tab alone. Open a page with
   `newBackgroundPage` (`bg-page.mjs`) and record `page_mode`.
4. `goto(url, {waitUntil: 'domcontentloaded', timeout: 20000})`.
5. Loop up to 25 s:
   - page host is `localhost` or `127.0.0.1` → `outcome: "loopback"`; done.
   - body text matches `/stay signed in\?/i` → `outcome: "kmsi"` (hand-off).
   - body text matches `/enter password|enter your password|verify your identity|approve sign in request|enter code|more information required/i`
     → `outcome: "signin_required"` (hand-off; record the matched phrase as
     `challenge`). Never type anything.
   - tile present and not yet clicked → click it with the `clickEl` approach
     from e2e.mjs (copy the function, with a comment naming its source).
     Select the tile with `[data-test-id="${CSS.escape(account)}"]`, falling
     back to a case-insensitive match of the attribute in page script.
     Record `clicked: true`, then **wait up to 10 s for the main frame's URL to
     change** before sampling the page again (the redirect takes ~1 s; a poll
     that lands before it still shows the picker).
   - tile already clicked and the picker still showing after that wait →
     `outcome: "picker_stuck"`. This is a mechanical failure (the tile changed,
     the click was lost, the page hung), not a sign-in demand: no hand-off,
     the tab is closed, and the job maps it to `no_loopback`.
   - otherwise sleep 1 s.
   Timeout → `outcome: "stalled"` with the last host, path and the first 200
   characters of body text.
6. Always: write the result JSON (`ts, outcome, clicked, page_mode, final_host,
   challenge, awaiting_human, error`) and disconnect. On a hand-off
   (`signin_required`, `kmsi`) leave the page open in the background and set
   `awaiting_human: true`, as e2e.mjs does; otherwise close it, bounded by 5 s.
   Exit 0 for `loopback`, 2 for a hand-off, 1 otherwise. A SIGTERM handler
   writes `outcome: "timeout"` and exits 124 (pattern from e2e.mjs).
7. `--raise` (the alert's "Open sign-in page" button): bring to the front a tab
   matching step 3's description. If none exists, open in the foreground
   `https://login.microsoftonline.com/<AZ_TENANT>/oauth2/v2.0/authorize` with
   the Azure CLI `client_id`, `response_type=code`, `redirect_uri=http://localhost`,
   the pinned scope, `login_hint=<AZ_ACCOUNT>` and **`prompt=login`**, which
   forces a real authentication (a `/login` POST, so rule 5 fires on the next
   run). The redirect to a closed localhost port afterwards is harmless. Never
   fall back to any other host's tab (`raise-signin.mjs` falls back to Google
   tabs, which is why it is not reused here).

**Verify by hand** against a scratch config, never the Mac's `~/.azure`:

```bash
t="$(mktemp -d)"; trap 'rm -rf "$t"' EXIT
printf '#!/bin/bash\necho "$1" > "%s/url.txt"\nexit 0\n' "$t" > "$t/open.sh"; chmod +x "$t/open.sh"
( AZURE_CONFIG_DIR="$t/cfg" BROWSER="'$t/open.sh' %s" perl -e 'alarm 120; exec @ARGV' \
    az login --tenant "$(security find-generic-password -s az-tenant -w)" --only-show-errors -o none </dev/null
  echo "azrc=$?" ) &
# wait for $t/url.txt, then, from ~/.local/lib/gcloud-reauth (after copying az-login.mjs there):
AZ_ACCOUNT="$(security find-generic-password -s az-account -w)" AZ_TENANT=... node az-login.mjs "$t/url.txt" "$t/result.json"
```
Expected: `result.json` outcome `loopback`, then `azrc=0`.

### Task 2: `az_tool.py` probe, install and fingerprint

**Files:** create `assets/gcloud-reauth/az_tool.py`,
`assets/gcloud-reauth/test/test_az_tool.py`.

Stdlib only. Constant: `CLI_CLIENT = "04b07795-8ddb-461a-bbee-02f9e1bf7b46"`.
**Every subcommand takes the account as an explicit argument**; nothing reads
`AZ_ACCOUNT` from the environment (ssh forwards only `LANG`/`LC_*`, so an env
variable would silently be empty on the remote). Paths go through
`os.path.expanduser`, since a quoted `~` reaches the remote tool unexpanded.

**Remote invocation, one layout for every subcommand:**

```bash
b64="$(base64 < "$LIB/az_tool.py" | tr -d '\n')"
[ "${#b64}" -lt 100000 ] || { record error "az_tool.py too large for one ssh argv"; exit 1; }
"$SSH" -o ClearAllForwardings=yes "$REMOTE" \
  "python3 -c 'import base64,sys;s=sys.argv.pop(1);exec(base64.b64decode(s))' $b64 <subcommand> <args...>"
```

(The whole remote command is one `bash -c` argument, capped by Linux's
128 KiB `MAX_ARG_STRLEN`; the check keeps a margin. The base64 alphabet needs no
quoting.) `sys.argv` after the pop is `['-c', <subcommand>, ...]`, the same
shape as a local `python3 az_tool.py <subcommand> ...` after `argv[0]`.

Account matching: an entry belongs to the account when its `home_account_id`
equals that of an `Account` entry whose `username` matches the account,
case-insensitive.

- `fingerprint <cache> <account>`: print `sha256(secret)[:16]` of the account's
  `CLI_CLIENT` RefreshToken, or `none`.
- `strip <in> <out> <account>`: write only the account's `Account`, `IdToken`
  and `RefreshToken` entries, plus `AppMetadata`, to `<out>` (mode 0600). No
  `AccessToken`, and no other account's entries (other accounts on the Mac
  must never reach the remote).
- `probe <azure-dir> <az-binary> <account>`: proves the refresh token without
  touching the real cache.
  1. Read `<azure-dir>/azureProfile.json` (utf-8-sig), retrying up to 3 times
     on a JSON error (az rewrites files in place). Find the subscription with
     `isDefault: true`: none, or no profile file → `profile_missing`; its
     `user.name` is not the account → `profile_mismatch`. (az picks the default
     subscription's user, so "some subscription matches" is not enough.)
  2. `tempfile.mkdtemp(prefix=".az-reauth.probe.", dir=<azure-dir>)` (same
     trust domain, not `/tmp`). Copy `azureProfile.json`, `clouds.config`,
     `config` and `commandIndex.json` where present, and the token cache
     stripped as `strip` does (read with the same 3-try retry).
  3. Run `<az-binary> account get-access-token --resource https://storage.azure.com -o none`
     with `AZURE_CONFIG_DIR` set to the temp dir, a 60 s timeout, stdin
     `/dev/null`; capture stderr.
  4. Classify: exit 0 → `ok`; stderr containing `AADSTS`, `invalid_grant`,
     `interaction_required` or `az login` → `failed <AADSTS code if any>`;
     "No subscription found" → `profile_missing`; anything else (DNS,
     connection, timeout, exit 127, an exception in the tool) → `error`.
  5. Delete the temp dir in a `finally`. Print the verdict, exit 0.
  The probe's refreshed token stays in the discarded copy; the real cache is
  never written, so the on-disk refresh token is never rotated by a probe.
- `install <target-cache> <account>`: read the staged cache from **stdin** (so
  it never touches disk outside the target directory) and merge it:
  1. Validate: JSON object; exactly one `CLI_CLIENT` RefreshToken, for the
     account; no `AccessToken` section; no entry with any other
     `home_account_id`. Otherwise print `invalid`, exit 3.
  2. Take az's lock the way msal-extensions does, with a stale rule:
     loop up to 30 s on `os.open(lock, O_CREAT|O_EXCL|O_WRONLY, 0o600)`. If
     the lock file exists and its mtime is older than 60 s, treat it as stale
     (left by a killed process): open it without `O_EXCL` instead. Then
     `fcntl.flock(fd, LOCK_EX|LOCK_NB)` in a loop bounded at 30 s. Timeout →
     `lock_timeout`, exit 4.
  3. Inside the lock: read the current target (missing → `{}`; 3-try retry),
     drop every entry in every section whose `home_account_id` equals the
     staged account's, insert the staged entries, write to
     `tempfile.mkstemp(prefix=".az-reauth.", dir=<target dir>)` (0600),
     `os.replace` onto the target, `os.utime(target)`.
  4. Unlink the lock file **before** releasing the flock (closes msal's own
     small window), then `flock(LOCK_UN)` and close.
  5. Re-read and print `installed <fingerprint>`, exit 0.
  6. On any exception, remove our temp file before exiting non-zero.
  The sweep of `<target dir>/.az-reauth.*` older than 10 minutes (files with
  `os.remove`, the probe's directories with `shutil.rmtree`) runs **before**
  step 2, best-effort inside its own `try`: it must never change the exit
  status of an install.

Tests (`python3 -m unittest`, temp dirs, a fake `az` script for `probe`):
- fingerprint picks the right account; `none` without one;
- strip of a two-account cache keeps only the named account, no AccessToken;
- probe: `profile_missing` (no file; no default), `profile_mismatch` (default
  subscription for another user while another subscription matches), `ok`,
  `failed AADSTS70043` (fake az prints the real error text), `error` (fake az
  prints a connection error; fake az missing); the real cache is
  byte-identical after each; no `.az-reauth.probe.*` dir remains;
- install merges: another account's entries survive, ours are replaced, no
  AccessToken arrives; input with a second account is refused; invalid input
  leaves the target byte-identical;
- install vs the real lock: a child process creates `<target>.lockfile` with
  `O_EXCL` and holds it for 2 s → install waits and succeeds, lock file gone;
  a lock file with an mtime 5 minutes old and no holder → install succeeds at
  once;
- the remote layout: run `python3 -c '<bootstrap>' <b64> fingerprint ...`
  locally and compare with the direct call;
- optional integration (skipped when `msal_extensions` cannot be imported from
  the az closure): a concurrent `PersistedTokenCache.modify` loop against
  repeated installs never yields invalid JSON.

Run: `python3 -m unittest discover -s assets/gcloud-reauth/test -p 'test_az_*.py' -v`.

### Task 3: `az_tool.py` decision

**Files:** extend `assets/gcloud-reauth/az_tool.py` and its test.

`last-signin <History>`: copy `History` and, if present, `History-journal`
together into a temp dir and open the copy **read-write** (so sqlite rolls back
a write caught in flight; `mode=ro` cannot). Print the latest visit time,
ISO-8601 UTC, of a URL on host `login.microsoftonline.com` whose path ends in
`/login`, preferring visits whose `transition & 0xff == 7` (FORM_SUBMIT) and
falling back to any visit on such a URL if that column is missing. Chrome times
are microseconds since 1601-01-01. Print `unknown` on any error.

**State is a fold over `az.jsonl`**, computed by `decide` (one bad line is
skipped, never fatal):
- `login_anchor`, `login_at`: from the latest row whose outcome is a successful
  login (`refreshed`, `recovered`, `install_partial`);
- `mac_anchor`, `remote_anchor`: the anchor each host's cache last received.
  A login updates `mac_anchor` (and `remote_anchor` when the remote install
  succeeded); a `pushed` row updates only `remote_anchor`;
- `last_attempt`: the latest row whose outcome is not one of the quiet
  `not_due`, `skipped`, `backing_off`, `interrupted`.

`decide <az.jsonl> <last-signin> <mac-probe> <remote-probe> <force>` (a probe
argument is a probe verdict, `unreachable`, or `skip` for a host excluded by a
profile problem) prints
`<action> <reason>`, action one of `login`, `push_remote`, `not_due`,
`backoff`. Rules, first match wins:

1. `force` = yes → `login forced`.
2. `last_attempt` failed (any outcome except `refreshed`, `recovered`,
   `install_partial`, `pushed`, `signin_required`, `kmsi`, `profile_missing`,
   `profile_mismatch`) less than 2 h ago → `backoff last_failed`.
3. `remote-probe` is `ok`, `failed...` (not `unreachable`, `error`,
   `profile_*`), `mac-probe` = `ok`, and either `remote-probe` starts with
   `failed` or `remote_anchor` < `mac_anchor` → `push_remote remote_behind`.
   (No Entra login needed: the Mac's cache carries the same lineage. Before
   the sign-in rules, because it needs no sign-in.)
4. No successful login ever → `login never`.
5. `last-signin` is a time later than `login_anchor` → `login new_signin`.
6. `last_attempt` is `signin_required` or `kmsi`, less than 6 h old →
   `not_due awaiting_signin`. (A login cannot succeed until a real sign-in
   happens; rule 5 above already let a new sign-in through.)
7. `mac-probe` starts with `failed` → `login check_failed`.
8. `login_at` older than 6 h → `login age`.
9. Otherwise `not_due fresh`.

**Offline guard:** unless `force`, when the result is `login` and `mac-probe`
is `error`, print `not_due offline` instead (a login on a laptop without
network ends in an alert and a backoff, not a token).

`error` and `profile_*` probe results never trigger a login on their own.

Tests: every rule; a corrupt jsonl line is skipped; after `install_partial`,
three hours of runs with the remote `unreachable` → `not_due` each time, never
`login` or `push_remote`; after `pushed`, the next run → `not_due fresh`;
`signin_required` followed by an hour with no new sign-in → `not_due
awaiting_signin`; age > 6 h with `mac-probe` `error` → `not_due offline`; new
sign-in with `mac-probe` `error` → `not_due offline`; a History fixture (sqlite
with Chrome's `urls`, `visits` incl. `transition`) returns the latest
FORM_SUBMIT `/login` visit and ignores `/oauth2/...` and `/reprocess`; a copy
with a hot journal returns a time or `unknown`, never a crash.

Commit.

### Task 4: `az-refresh.sh`, the job

**Files:** create `assets/gcloud-reauth/az-refresh.sh`.

Header comment: why it exists (facts 1, 2, 5), the direction (the Mac logs in,
the cache is merged into both hosts), the anchor rule, the consequences (one
shared refresh-token lineage: `az logout` on either host kills both; a manual
`az login` on either host is replaced at the next login while the isolated
Chrome's session is good), and what each outcome means.

Env:
- required: `REAUTH_REMOTE`, `AZ_TENANT`, `AZ_ACCOUNT` (Keychain
  `gcloud-reauth-remote`, `az-tenant`, `az-account`);
- optional: `REAUTH_CDP_URL`, `REAUTH_HARNESS_DIR`, `REAUTH_STATE_DIR`,
  `REAUTH_NODE`, `REAUTH_AZ` (default `az`), `REAUTH_CHROME_HISTORY` (default
  `~/Library/Application Support/Chrome-gcloud/Default/History`),
  `REAUTH_LOCAL_AZURE_DIR` (default `~/.azure`), `REAUTH_OSASCRIPT`, and
  `REAUTH_SSH` (default `ssh`; tests only).
- Usage: `gcloud-reauth-az [--force]`.

Every path ends in exactly one `az.jsonl` row via `record`. Every az, ssh and
node call has a `timeout`. Remote calls use the one invocation layout from
Task 2, with the account passed as an argument.

1. Full-wake wait (copy `full_wake` from refresh.sh, with a pointer comment).
2. `mkdir "$STATE/az.lock"` (stale after 30 min). Held → record `skipped`, exit
   0. Then `WORK=$(mktemp -d "$STATE/az-run.XXXXXX")` (0700), and sweep
   `$STATE/az-run.*` dirs older than 30 min (left by a SIGKILL; they hold a live
   refresh token). EXIT trap: remove `$WORK`, release only our own locks.
3. `last_signin=$(python3 az_tool.py last-signin "$HISTORY")`. If `unknown`,
   touch `$STATE/az-history-unknown-since` unless it exists; otherwise remove
   it. Every row carries `last_signin`.
4. Probes:
   - Mac: `python3 az_tool.py probe "$LOCAL_AZ" "$AZ" "$AZ_ACCOUNT"`.
   - Remote: `probe '~/.azure' az "$AZ_ACCOUNT"` through the Task 2 layout,
     timeout 90, retried 4 × 15 s on ssh failure; ssh exit 255 or timeout →
     `unreachable`.
   - A host whose probe is `profile_missing`/`profile_mismatch` is **excluded**
     for this run (no install there) and reported in the row's `profiles`
     field; the run carries on for the other host. Both excluded → record
     `profile_missing`/`profile_mismatch` and exit 1.
     With only the Mac excluded, a login still runs (the staging login and
     its probe use `$WORK/cfg`, not `~/.azure`) and installs on the remote
     only: that row sets `remote_anchor` and leaves `mac_anchor` alone.

     the offline guard treat as "no Mac signal" (no push, no `check_failed`,

     fails and backs off.

   `cdp_unreachable`.

## Risks and how the plan handles them

- **Anchor rule wrong** (fact 2 has one confirmation): rule 8 (6 h cadence)
  keeps logging in, and rule 7 recovers a dead token within about an hour of
  it dying. A rule-7 login is a `recovered` row that alerts, so a wrong anchor
  rule cannot hide behind green rows.
- **Concurrent az on the remote writes an old-anchored token back** (fact 10):
  not preventable by any lock. The remote probe then fails when that token dies,
  rule 3 pushes the Mac's cache with no login, and the row is `pushed` with
  `recovered: true`, which alerts, so it is visible. Expected rare.
- **Chrome History unreadable**: `unknown` → rule 5 never fires; rules 7-8 carry
  it; after 24 h the job alerts `history_unreadable`.
- **Offline laptop**: probes report `error`, which never triggers a login or an
  alert.
- **Entra changes the picker**: `stalled` → `no_loopback`, alerted; 2 h backoff.
- **Sign-in log noise**: about 4-5 silent az logins a day (6 h cadence plus one
  per real sign-in); none while the remote is down (rule 3 pushes instead) or
  while a sign-in is awaited (rule 6).
